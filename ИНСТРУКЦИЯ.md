# Что нужно сделать вам (то, что я сделать не могу)

CircleCI заменён на **GitHub Actions** (он работает прямо в GitHub, отдельная регистрация не нужна). Конфиг лежит в `.github/workflows/ci.yml`.

## 1. Git и GitHub
В папке проекта `circleci-lab` выполните:

```bash
git init
git add .
git commit -m "Initial commit: simple app with tests and GitHub Actions"
```

1. На https://github.com создайте **публичный** репозиторий (без README).
2. Затем:

```bash
git remote add origin https://github.com/ВАШ-ЛОГИН/circleci-lab.git
git branch -M main
git push -u origin main
```

## 2. Проверка пайплайна
1. Откройте репозиторий → вкладка **Actions**. Workflow `CI` запустится автоматически после push.
2. Убедитесь, что оба job (`Run tests` и `Check formatting (black)`) имеют статус **Success** и выполнялись параллельно.
3. Откройте каждый job и изучите логи шагов (Install dependencies, Run tests, Check code formatting).
4. Сделайте скриншоты для отчёта: граф workflow и логи шагов.
5. Если `black --check` упал: `pip install black && black .`, затем commit и push.
6. Для проверки кэша сделайте ещё один push: в шаге Set up Python должно появиться «Cache restored».

## 3. Ответы на контрольные вопросы (кратко)
1. **CI/CD** — практики автоматизации сборки, тестирования и доставки ПО; сокращают время до релиза и выявляют ошибки раньше.
2. **Формат конфигурации** — YAML (в GitHub Actions: `.github/workflows/*.yml`; в CircleCI: `.circleci/config.yml`).
3. **`jobs`** — отдельные задания: среда выполнения (`runs-on` / executor) и список шагов (`steps`).
4. Раздельные шаги дают понятные логи (видно, упала установка или тесты), позволяют кэшировать зависимости и переиспользовать шаги.
5. В GitHub Actions доступ к репозиторию автоматический (токен `GITHUB_TOKEN`, шаг `actions/checkout`). В CircleCI — через OAuth-приложение GitHub / deploy key.
6. Да: для GitHub Actions — утилита `act` (запускает workflow локально в Docker); для CircleCI — `circleci local execute`.
